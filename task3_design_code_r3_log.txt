## 開發流程

每個任務照這個順序走，前一步沒完成就不進下一步。

1. **寫 Design.md**：放在 `planning/<任務>/Design.md`，一個任務一份。設計與實作步驟寫在同一份，不另外開 Implementation.md。內容：
   - 目標與範圍
   - 圖：依任務挑流程圖、時序圖或架構圖（Mermaid），用得上的才畫
   - 現況（附檔案與行號）
   - 做法與實作步驟（要改哪些檔、依什麼順序）
   - 資料變更
   - 完成條件（可量測、可重現）
   - 風險
2. **Design 審查**：依序做 Spec → Code → Security 三階段，每階段的阻擋問題修完才進下一階段。
3. **實作**：由 OpenCode（`opencode run`）照 Design.md 的步驟做；做法有變更就先改 Design.md，再改程式。主導的 agent 負責拆工作、核對結果、跑測試與建置。
4. **實作審查**：同樣依序做 Spec → Code → Security。
5. **收尾**：更新受影響的 `Agents/` 文件與 `planning/ROADMAP.md` 的狀態，重建 release exe。

## 專案指示檔與知識文件

- **指示檔：** 專案指示檔統一使用根目錄的 `AGENTS.md`。專案若仍有 `CLAUDE.md`，將其內容依下列分工併入 `AGENTS.md` 與 `Agents/` 後移除；專案沒有 `CLAUDE.md` 時略過。
- **`AGENTS.md` 只放跨任務都適用的通用規則**（工作方式、必讀順序、禁止事項、驗證方式），專案知識只用連結指向 `Agents/`，連結文字寫明「什麼情況要讀」。
- **`Agents/` 維護五個知識主題**，每主題一份文件：服務架構（含各功能的前後端歸屬）、系統架構、資料庫結構、業務邏輯、使用者權限。可依專案需要增加主題，但同一主題不拆成多份。
- **停用 `maintenance.md`：** 專案若有 `maintenance.md`，把 Agent 需要的資料與規範拆入對應的 `Agents/` 主題或 `AGENTS.md` 後停用；沒有則只建立並維護 `Agents/`。
- **開工讀取：** 只讀本次任務受影響的 `Agents/` 主題；任務改變架構、資料表、業務規則或權限時，於交付前回寫對應主題並更新其文件基本資訊。
- 知識文件以現有程式碼為準；與程式不一致時依程式修正文件，並於任務 Design 記錄差異。

## 文件分工

| 文件 | 撰寫與維護者 | 用途 |
| --- | --- | --- |
| Planning（沿用使用者的實際檔名，如 `planning.md`） | 使用者 | 需求、目標、範圍與限制。Agent 讀取並引用，未經明確指示不改寫、改名或刪除 |

- `Design.md` 是每個任務在開發流程中各自產出的文件，合併原本的設計與實作紀錄，不另外產出 `implementation.md`；整個專案不共用一份 Design.md，跨任務知識放 `Agents/`。

- 設計階段寫預期行為與驗證方法，實作階段才填實際結果；保留重要設計修訂理由及前後差異，不事後改寫成從未變動。

## 審查：兩個時點，每次三階段

審查在兩個時點進行：**設計完成後（實作前）** 與 **實作及驗證完成後**。每個時點都依 **Spec → Code → Security** 執行三個階段，分別保留結論，不能以一次籠統的「審查通過」取代。每個時點可複查多次直到收斂，次數不設上限。

| 階段 | 設計審查 | 實作審查 |
| --- | --- | --- |
| Spec（規格） | 將 Planning／需求原文與 Design 並排核對：範圍、前後端責任、適用的正常／邊界／失敗行為、契約與可判定驗收；不以 Agent 摘要取代原規劃 | 逐項比對 Planning、Design 與實際行為；檢查漏做、偏離、回歸與測試證據，確認未完成項目已明列 |
| Code（程式與可實作性） | 讀取受影響現有程式與呼叫者，審查預定修改路徑、相容性、資料遷移、並行與可測性；新模組尚無程式時審查設計契約並記錄限制 | 讀取實際差異及上下游路徑，檢查正確性、錯誤處理、持久化、相容性、測試有效性與可維護性 |
| Security（資安） | 檢查信任邊界、身分驗證、後端授權、資料裁切、敏感資訊、輸入、外部副作用及部署限制 | 核對實際程式與設定的授權／拒絕路徑、敏感資料處理、輸入與外部整合；依變更風險使用適合的資安檢查 |

純文件任務的 Code 階段審查來源、路徑、連結與規則可執行性；Security 階段審查資訊揭露與安全規範是否遺漏。仍須留下紀錄，不能聲稱已做產品程式審查或完整資安掃描。

| 階段 | 設計審查 | 實作審查 |
| --- | --- | --- |
| Spec | 無專用技能，依上表並排核對 Planning 與 Design；系統規格文件另依 `system-spec-writer` 的品質檢查 | `code-reviewer` 的 `references/spec-compliance-review.md`：缺漏需求、多餘新增、理解落差 |
| Code | 無專用技能，依上表讀取受影響程式與呼叫者 | `code-reviewer` |
| Security | 無專用技能，依上表檢查信任邊界與授權 | `security-reviewer` |

使用這些技能時，本技能的規則優先：

- **範圍基準：** 以 Planning 與已確認決策為準。`spec-compliance-review.md` 的「缺漏需求」只計 Planning 要求的項目；其檢查清單中的邊界情境，Planning 未要求者不構成阻塞。「多餘新增」照常檢查，即擴充範圍。
- **分類對應：** 技能輸出的 Critical／Major／Minor 或 Critical／High／Medium／Low 嚴重度，不直接等於本流程的結論。符合「阻塞」定義且附依據者列阻塞；其餘列建議或範圍外。技能的 Verdict（Approve／Request Changes）改以本流程的「需修正／受阻／通過」記錄。
- **資安審查方式：** `security-reviewer` 只做程式與設定的唯讀審查，以及本機已安裝工具的靜態掃描。主動測試、滲透測試、對任何執行中環境的攻擊性測試，須使用者明確授權並界定範圍；正式環境不得測試。
- **來源：** `code-reviewer`、`security-reviewer` 取自 `Jeffallan/claude-skills`（MIT），commit `36f3fe8`，2026-10-21 安裝；Codex 與 Claude 各存一份。

## 發現、修正與複查

- **紀錄：** 每一階段記錄時點（設計／實作）、第幾次複查、日期、審查者及方法、審查版本與檔案範圍、發現位置與影響、修正、複查證據及結論，存於該任務的 Design。
- **結論：** 使用「待審查」「需修正」「受阻」「通過」。沒有實際審查或缺少必要證據時保持待審查／受阻。沒有相關風險時寫「已檢查，無此類變更」，不可跳過整個階段。
- **阻塞：** 只限核心行為不明確、權限錯誤、資料遺失風險、驗收無法判定，或可核對的事實錯誤。修正後複查該階段及受影響的後續階段。
- **阻塞須附依據：** 每條阻塞須指出所違反的 Planning／需求原文、已確認決策，或錯誤事實的檔案與行號；指不出依據者最多列為建議。「缺少某類邊界情境」本身不構成阻塞，除非 Planning 要求，或缺少它會使驗收無法判定。
- **建議與範圍外：** 建議不計入結論。會擴充範圍的建議最多列一行「供使用者決定」，未經同意不納入 Design。
- **最小修正：** 作者只修正阻塞，以更正或刪除為主，不以新增規格、邊界案例、驗收或測試作為修正手段；需要新增規格才能修正時，轉交使用者決定。
- **複查範圍：** 第二次起，審查者只確認上一次的阻塞是否關閉，以及本次修改是否引入新阻塞；未修改的內容不重新全面審查。需求或設計方向改變時，才對受影響章節重新全面審查。
- **交給使用者決定：** 同一階段連續兩次複查仍有阻塞，或阻塞數量未下降時，Agent 停止自行修改，把剩餘發現、各自依據與可行選項交給使用者。這不代表審查結束，使用者決定後照常繼續複查直到通過。
- **審查提示：** 委派其他 Agent 審查時使用 [審查提示範本](assets/Review-Prompt.md)；作者自審也依同一標準分類發現。
- **獨立性：** 審查回覆與作者自驗分開。有獨立審查者時讓其直接閱讀需求、Design、相關程式及驗證證據。未實際委派時不得宣稱第三方審查；不得擅自向外部模型傳送內部資料。
- **進入實作：** 設計審查三階段皆通過才能實作。涉及人員核准或外部操作時，另遵使用者授權；審查通過本身不授權發布或部署。
- **多 Agent 協作：** 開始時安排獨立驗證角色，持續檢查關鍵路徑與整合衝突；是否委派依使用者及當次指示。
- **知識回寫後：** 回寫若改變設計、權限或安全規範，複查受影響階段；最後檢查 Design、專案知識與實作一致。

## 交付判定

Design 必須包含實際變更、已執行的驗證及證據、設計審查與實作審查各三階段的紀錄、未完成項目與環境限制。功能完成、正式部署與真人驗收分別記錄；未部署不得寫成已上線。驗證方式依專案的驗證規則。

# 系統文件撰寫與審核規範

本技能管理系統文件的共同撰寫、審查與交付要求，不取代需求分析、架構設計或繪圖技能。首次套用時必須完整讀取 [28 條核心規範](references/core-rules.md)。該檔是使用者規範的唯一維護來源；以下為執行方式，依使用者澄清維持相同語義。使用者當次明確指示優先；相關技能及範本的預設與本規範衝突時，依本規範調整。

## 適用與協作

- 系統規格工作搭配 `system-spec-writer`；架構文件搭配 `system-architecture-doc`；圖表搭配 `system-architecture-diagrams`。僅讀取本次需要的技能，不為小幅文字修訂擴大工作。
- 本技能可單獨審核系統文件。使用者只要求審核時，列出問題，不擅自重寫。
- 共用規範與上述技能並列安裝；引用缺失時先確認路徑，無法讀取就說明缺失，不宣稱已套用。不得循環載入已讀取的技能。

## 撰寫與更新

1. 先讀已提供的需求與相關文件，辨識本期範圍、既定名稱、文件版本及可信來源。來源依可靠性、確認狀態與適用範圍判斷；已確認的內部需求、既有設計與程式碼可以使用，未確認草稿不作定案依據。正文先概述必要內容，再補充章節或來源連結，不要求讀者自行找其他文件來理解核心設計。
2. 文件預設使用台灣繁體中文，只有使用者明確要求時才改用其他語言；適用於正文、標題、圖表標籤及說明。使用客觀、精煉的主動語態。專業術語與代號首次交代中文名稱和意義，有通用或已確認縮寫時採「中文（英文縮寫）」。沒有縮寫時使用中文或必要英文全名，不為命名而創造縮寫或提出不必要問題。正文與圖表優先使用業務名稱；需保留技術名稱時先定義，不能讓閱讀者猜測。
3. 欄位定義與介面契約是第 24 條所要求的技術內容：可在欄位表、契約、程式碼區塊及確有技術必要的說明保留精確名稱，附中文業務意義與用途。未定義的自創變數或代號不得直接出現；一般業務正文使用業務名稱。
4. 先將各文件以 Markdown 寫入 `docs`，可依專案慣例使用子目錄。更新時沿用文件身分、版本與需求編號；既有檔案不在 `docs` 時不擅自搬移或刪除，指出路徑差異，依開發者明確指示處理。只在開發者要求後才轉出 Word 或 PDF。
5. 文件開頭提供「文件基本資訊」：名稱、版本、建立日期、更新日期與各章節變更摘要。日期與歷史版本沒有依據時不捏造。標題最多四級，細分使用項目符號或粗體。
6. 主動規劃資料流：來源、驗證與轉換、儲存、傳出及結果；同時交代正常、邊界及錯誤行為。將非本期實作項目集中於「非本期範圍（Out of Scope）」獨立章節。
7. 說明採用技術的選用理由。涉及架構與資料流時，獨立說明身分驗證、適用權限控管模型及傳輸加密標準；只有採用角色權限控管（RBAC）時才展開角色權限，不強制套用此模型。資訊足夠時建立非功能性需求章節，涵蓋效能、併發、資料保留及可用性；未知值列問題，不捏造。
8. 系統介接或 API 依實際協定描述契約。HTTP 介面包含方法、端點、欄位、請求、回應、狀態碼與錯誤代碼；其他介接描述通道或位置、資料格式、處理結果、錯誤及適用的重送行為，不硬套 HTTP 欄位。範例不得引入未確認行為。
9. 圖表優先保留 Mermaid 或其他可編輯程式碼，讀取相應圖型規範；名稱、資料庫、箭頭動作及正文一致。轉出 Word／PDF 時，圖號與圖名在圖下，表號與表名在表上。
10. 每個主要功能定義業務驗收條件與預期結果，依交付需求納入正式文件。內部交付前的品質檢查、自查流程與審核紀錄另存 `docs/internal/<主題>/Delivery_Checklist.md`；詳細測試案例可另存 `AC_List.md`，不因其為內部案例而刪除正式文件的業務驗收章節。Markdown 工作草稿可保留明確標示的討論、假設與待決方案；正式文件移除這些內容，必要待確認問題仍可列出，但不能寫成已決方案。

## 審核與連動更新

需要保存內部交付前檢查時使用 [交付檢查範本](assets/delivery-checklist-template.md)，不以該檢查清單取代正式文件的業務驗收章節。

- 審查架構完整性、設計合理性、與其他文件是否矛盾，以及來源可靠性。追蹤代表性資料從輸入到結果，檢查失敗後的資料狀態與恢復方式；核對技術選型是否支持需求。
- 長文件分章產出。每新增或修改一章，核對前置章節的名詞、元件、資料流、介面與圖表；同步更新受影響的資料描述及內部驗收，不只修正文句。
- 輸出審核問題時交代文件位置、證據、影響、修正建議與需開發者決定的事項；來源不足或架構矛盾要提出討論。可繼續不受影響的草稿工作，不宣稱疑義已解除。
- 使用其他 Agent 工具審核時，要求第三方專家角度，不暗示預期結論。提供文件、相關架構及必要來源，要求檢查完整性、合理性、跨文件矛盾、來源可靠性及缺漏情境；僅比對正確性、拼字或措辭不足以判定正式交付。此規則規範已啟用的審核，不強制每次編輯都委派 Agent，也不授權向外部服務傳送文件。
- 正式交付前確認：基本資訊與章節變更齊全、術語一致、無含糊措辭或表情符號、非本期內容獨立、資料流含例外、安全機制及技術理由明確、契約完整、內部交付檢查與討論紀錄未混入正文，業務驗收條件完整、來源可核對。關鍵疑義未解時交付草稿及問題，不能標示正式完成。
- 交付說明列出文件位置、已檢查範圍與待開發者確認事項。自查、第三方 Agent 意見、人員核准與測試結果分開，不互相冒充。
# 系統文件核心規範

以下保留原 27 條規範的編號，並新增第 28 條語言規範，依使用者於 2026-10-09 的澄清修訂第 1、7、10、11、22、24、26 條。目的是防止未定義代號、以跳轉取代說明，以及內部工作流程混入正式文件；不得把助理建議冒充使用者要求。

1. 首次出現的專業術語或系統代號，必須先定義中文名稱與意義；有通用或已確認的英文縮寫時採「中文（英文縮寫）」格式，後續可使用縮寫。沒有縮寫時使用中文或必要的英文全名，不自行創造縮寫。不使用閱讀者無從理解的自創變數或代號；確實需要新識別名稱時，先說明用途、業務意義與定義。正文以業務描述優先，例如「目標起始時間」；需精確交代介面欄位或技術契約時可保留名稱，但必須附中文意義，不讓代號取代解釋。
2. 規劃文件撰寫時也要一併討論 Data Flow。
3. 文件架構先各自以 Markdown 格式寫到 `docs` 裡，開發者要求再產出 docx 檔案或 PDF 檔案。
4. 架構規劃需要審核的內容涵蓋架構完整性、是否與其他文件架構矛盾、來源是否可靠；有疑義就提出來跟開發者討論。
5. 使用其他 Agent 工具審核時，應讓其以第三方的角度給予意見，評估架構設計是否完整、是否合理；僅比對正確性或用字遣詞，不足以達到可以產出正式文件的程度。
6. 避免在規劃文件中出現含糊不清的用詞，如「團隊算法訓練」，一定會被挑戰「這是什麼意思？具體來說要做什麼？」。
7. Markdown 工作草稿可保留清楚標示的內部討論、假設與待決方案。正式文件保持客觀專業，移除口語化討論過程及未定案的推測性描述；決策背景轉化為客觀的技術選型理由或業務需求背景。正式文件可列具體待確認問題，不把未決方案寫成已核准設計。
8. 明確界定系統範圍（Scope）：正式文件應專注於本期將實作的功能。若有在需求訪談中提及、但「本期不實作」的項目，嚴禁與正式功能混寫，必須統一歸納至「非本期範圍（Out of Scope）」獨立章節，避免客戶產生錯誤期待或驗收爭議。
9. 當規劃文件需要呈現架構圖、流程圖（Data Flow）或循序圖（Sequence Diagram）時，Agent 應優先輸出標準的 Mermaid 或程式碼，而非嘗試直接生成圖片檔，以利後續開發者調整圖表與統一渲染風格，並確保圖表內文字與內文一致。
10. 來源必須可靠、可追溯且支援對應主張。可使用已確認的內部需求、既有設計與程式碼；未確認草稿不能當成定案依據，未取得的外部文件不能虛構引用。正文應自足，不以要求讀者另看內部草稿、未公開文件或其他章節代替必要說明。涉及通用法規或公開技術標準時，提供官方來源名稱及可查證連結。
11. 先概述本段需要的內容、機制或結果，再以「詳見某某章節」補充細節位置。不得只寫「見第 X 章」或只提供文件連結，讓閱讀者自行拼湊必要背景；交叉引用是補充，不是替代說明。
12. 文件上下用詞要保持一致。
13. 規劃文件用的圖片產出時，務必參照相關類型圖片的撰寫規範，避免資料庫名稱沒有統一、添加不必要的符號、容易有歧義的動作名稱。
14. 套用的技術要說明選用理由。
15. 產出 docx 或 PDF 文件時，「圖 X」這類編號都放在圖片下方；表格編號放在表格上方。
16. 避免放置非常見用語，以免造成客戶或其他開發者困惑。
17. 替換中國用語，開發者面對的場景多為台灣的單位。
18. 正式文件不可出現表情符號或 Emoji。
19. 正式文件產出時，必須包含「文件基本資訊」區塊，包含文件名稱、版本號（如 v1.0）、建立／更新日期，以及各章節的變更摘要，以符合正式文件的管控規範。
20. 規劃文件與 Data Flow 不可只寫順利執行的流程（Happy Path）。Agent 必須主動規劃並補齊邊界條件（Edge Cases）與錯誤處理機制（如：API 呼叫逾時、資料格式錯誤、斷線重連機制），並於文件中說明對應的系統行為。
21. 為確保轉出 docx 或 PDF 時的目錄結構正確，Agent 在撰寫 Markdown 時，標題層級最多下探至第四級（`####`）。若需更細節的分類，強制改用項目符號（Bullet points）或粗體標示，避免文件目錄過度碎裂。
22. 涉及系統架構與資料流規劃時，獨立說明身分驗證機制、適用的權限控管模型與資料傳輸加密標準。採用角色權限控管（RBAC）時描述角色及權限；其他模型依專案需求說明，不強制所有系統使用 RBAC。不適用或尚未決定的項目必須說明理由或列待確認，不虛構已採用機制。
23. 若規劃文件字數過長，Agent 應分章節產出。產出新章節時，必須嚴格檢視是否與前置章節的「名詞定義」、「系統架構」與「Data Flow」保持一致，避免前後邏輯斷裂或架構圖與內文對不起來。
24. 系統介接或應用程式介面（API）依實際協定使用一致的契約結構，說明呼叫或發布方、接收方、欄位與中文業務意義、請求或訊息格式、回應或處理結果，以及錯誤代碼與失敗行為。超文字傳輸協定（HTTP）介面包含方法、端點結構、請求與回應格式、狀態碼及錯誤代碼；事件、訊息與檔案介接描述其通道或位置、資料格式、處理結果及重送等適用語義，不硬套 HTTP 欄位。精確欄位名稱可出現，但不得使用未定義的自創代號或以代號代替說明。
25. 除功能性流程與資安（如第 22 點）外，若資訊充足，Agent 應主動在規劃文件中建立「非功能性需求」章節，包含預期效能（Response Time）、併發處理量（Concurrency）、資料保留策略（Data Retention）與系統可用性（Availability）的設計原則。
26. 每個主要功能或複雜邏輯須具備驗收視角，建立預期結果與可判定的完成條件。正式文件可且應依交付需求包含業務驗收條件、系統預期結果及驗收範圍；不得混入 Agent 或團隊內部交付前的自查流程、審核清單、評分紀錄及內部討論。內部交付檢查另存工作檔；業務驗收內容與內部品質檢查必須明確區分。

28. 文件預設使用台灣繁體中文，涵蓋正文、標題、圖表標籤及說明；只有使用者明確要求時才改用其他語言。專業術語的英文名稱或縮寫、產品名稱及必要的技術契約名稱依相關規範保留，不因此改變文件的主要語言。

# 系統架構文件

產出讓業務、開發、維運與審查者能理解系統邊界、核對實作並檢驗設計的文件。文件預設使用台灣繁體中文，只有使用者明確要求時才改用其他語言；遵從使用者指定的契約章節與交付格式。此 skill 的規則是內部工作慣例，不等同任何認證標準。

## 共用文件規範

本技能用於系統規劃文件時，必須先讀取同層的 [系統文件撰寫與審核規範](../system-documentation-standard/SKILL.md)，並依其指示讀取 28 條核心規範。該規範優先於本技能與範本的交付預設；已讀取時不重複載入。僅處理獨立圖檔時採用相關命名、圖表及審查規則，不強制新增整份規劃文件。


## 選擇工作模式

- **新建完整架構書**：讀取 [撰寫 SOP](references/workflow.md) 與 [撰寫規範](references/writing-standard.md)，以 [架構書骨架](assets/architecture-template.md) 裁切章節。
- **單一功能 TDD**：讀取 SOP，使用 [TDD 骨架](assets/tdd-template.md)，交代變更前後、方案取捨、介面、失敗處理與 rollout，不強制擴成整本架構書。
- **從程式碼補文件／更新文件**：先鎖定版本與範圍；依 SOP 核對既有敘述。分開寫 As-is 與 To-be，保留未受影響內容與既有命名。
- **審查既有文件**：讀取 [審查規準](references/review.md)，提供證據、影響、修正與驗證方式；只有被要求修改時才改寫文件。
- 畫圖時讀取 [圖表邏輯](references/diagrams.md)；需要參考範例或解釋方法來源時讀取 [研究來源](references/sources.md)；需要示範如何串起證據、圖與驗收時讀取 [原創示例](references/worked-example.md)。不必每次重做網路研究。

## 工作底線

1. 先確認文件用途、讀者、系統邊界、版本與來源。優先讀取已提供資料；只詢問會改變主要架構或交付範圍的缺口，其餘列入待確認事項並繼續。
2. 對關鍵敘述區分 **已驗證、來源宣稱、假設、提案、待確認**。檔案存在不代表功能已部署；設計目標不代表量測成果；矛盾來源需並列版本與待裁決點。
3. 維持可追溯鏈：需求／品質目標 → 元件或介面 → 場景／圖 → 決策／風險 → 驗收方式。沿用專案 ID；無既有編號時只為需追蹤的項目建立 ID。
4. 先整理元件與關係，再繪圖；圖、正文、介面表使用同一名稱。未知拓樸、效能數字、模型準確度與已核准決策不可自行補成事實。
5. 深度以風險與讀者需要裁切。沒有適用性的內容寫明理由或省略；不得用大量空白章節冒充完整交付。草稿可保留明確缺口，正式完成判定依審查規準。
6. 交付前做跨章一致性與品質檢查，修正可直接修正的問題，保留仍需專案證據的事項。AI 自查不冒充人員簽核、測試執行或正式驗收。

# 架構文件審查規準

審查同時涵蓋設計完整性與合理性、與其他文件的架構矛盾及來源可靠性。正式正文不得混入內部討論、未定案推測或交付自查清單；業務驗收與追溯仍須依交付需求呈現。來源可靠性依確認狀態與主張檢查，不因內部來源而一律排除。委派其他 Agent 時要求第三方專家意見，提供位置、證據、影響與待討論問題，不以文字校對代替架構審核。

本規準是 skill 的內部品質檢查，非 arc42、C4 或任何標準機構的認證。區分文件品質、設計風險、實作符合性；有文件證據不代表系統測試通過。

| 證據與狀態 | 事實、假設、提案是否分開？現況屬哪一版本？ | 可重查的來源；量測與目標分離；矛盾有標記 |

## 問題分級

- **阻擋交付**：會讓讀者依錯誤事實做重大決定，或核心範圍完全不可判讀。例如虛構已驗證成果、重大圖文矛盾、核心介面／資料責任不明。阻擋的是正式交付判定，不是停止整理可用草稿。
- **重大**：關鍵品質或操作路徑無法驗收，例如重試寫入但未交代重複效果、必須遷移卻沒有失敗回復策略。
- **一般**：局部缺漏造成理解或維護困難，尚不影響主要方案判斷。
- **建議**：可讀性或表達改善，非必要整改。

根據具體系統風險調整級別；不要看到某個詞缺席就自動升級。只檢查使用者指定範圍，未檢查部分標為未審查。

## 結論與門檻

- **可送人員審查**：核心內容有足夠依據、無未解的阻擋／重大問題；提案與未知已清楚揭露。這不等同人員核准。
- **需修訂**：存在足以影響設計、維運或驗收判斷的缺漏／矛盾。
- **資訊不足，僅可作草稿**：現有證據不足以確認核心現況或需求，仍應交付已完成內容與具體補件清單。

45: `playback_pipeline.rs` `next_playing()`：
46: 
47: - 現行 `next_stream()`（line 397-400）從 `stream_source` 取得單一 `f32` 原生樣本，線程安全地鎖定 `stream_source` Mutex。
48: - `TrackResampler::process(sample: f32) -> Option<f32>`：餵入單一原生樣本，累積至 BLOCK_FRAMES（2048）後經 rubato 重取樣到 48kHz；回傳 `Some(48kHz 聲道樣本)` 或 `None`（累積中，非靜音，非結束）。**保留現有單樣本介面，不改為區塊介面。**
49: - `PlaybackCore` 新增兩個佇列：
50:   - `track_out: Mutex<VecDeque<f32>>`：TrackResampler 輸出的 48kHz 聲道樣本暫存，**尚未經 DSP**。
51:   - `dsp_out: Mutex<VecDeque<f32>>`：DSP 最終輸出佇列（立體聲交錯），供 `next_playing()` 逐樣本消耗並回傳。
52: - 修改 `next_playing()` 的串流軌分支（line 328-338）：
53:   1. 先從 `dsp_out` 佇列取樣本回傳；若不足兩個（一立體聲幀 `[L, R]`），繼續執行步驟 2-6。
54:   2. 呼叫 `next_stream()` 取得原生樣本。
55:   3. 鎖定 `track_resampler`，**必須**存在（長檔載入時 `player.rs:420` 已建立）；若為 `None` 回傳錯誤記錄並輸出靜音，不得繞過。
56:   4. 呼叫 `track_resampler.process(sample)`；回傳 `Some(s)` 時將 `s` 追加至 `track_out`；`None` 表示累積中，繼續拉取上游。
57:   5. 當 `track_out` 夠兩個樣本時，取兩個組成 `[L, R]`，送入 `apply_dsp_block(&[L, R], &mut tmp_out)`，將 `tmp_out` 全部追加至 `dsp_out`。
58:   6. 從 `dsp_out` 取樣本回傳。
59: - 上游結束（`next_stream()` 回傳 `None`）且 `track_out`、`dsp_out` 皆耗盡後，進入軌結束流程（見 4.3）。
60: - 移除 line 337-338 的繞過路徑（`resampler` 為 `None` 時直接 `apply_dsp(sample)`）。

62: ### 4.2 apply_dsp_block 改為立體聲幀輸入、零到多幀輸出並併入 RateStage（R3）
63: 
64: `playback_pipeline.rs`：
65: 
66: - `PlaybackCore` 新增欄位：
67:   - `rate_stage: Mutex<Option<RateStage>>`（`RateStage` 在 `crate::dsp`，`dsp.rs:540`）；
68:   - `track_out: Mutex<VecDeque<f32>>`（TrackResampler 輸出暫存，未經 DSP）；
69:   - `dsp_out: Mutex<VecDeque<f32>>`（DSP 最終輸出佇列，立體聲交錯）；
70:   - `dsp_params: Mutex<Option<FxParams>>`（參數快照，命令執行緒更新，音訊執行緒讀取）。
71: - `PlaybackCore::new()`（line 135-162）中初始化 `rate_stage: Mutex::new(None)`、`track_out: Mutex::new(VecDeque::new())`、`dsp_out: Mutex::new(VecDeque::new())`、`dsp_params: Mutex::new(None)`。
72: - `dsp.rs` 需修正：`RateStage::new(channels: usize, sample_rate: u32)` 與 `RateStage::run(&mut self, input: &[f32], p: &FxParams, flush: bool, out: &mut Vec<f32>)` 目前為私有（line 547、550），須改為 `pub(crate)`，以便 `playback_pipeline.rs` 跨模組呼叫；`run` 保留 `&FxParams` 參數；`new()` 的 `channels` 參數為 `usize`，呼叫處傳入 `INTERNAL_CHANNELS as usize`。
73: - `FxParams` 沒有 `allow_rate` 欄位（`allow_rate` 是來源建構參數，見 `dsp.rs:617、630`）。以來源類型（本地長檔建立並啟用 RateStage、電台串流略過 RateStage，與 `Agents/business-logic.md` 第 99 條一致）決定是否建立／略過 RateStage。
74: - FxChain 必須經 `dsp.rs:311-324` 的 `set(&params)` 更新設定及配置效果狀態，再於每個立體聲幀上呼叫 `frame()`。
75: - 軌載入/切換時（初次載入、手動換軌、seek、自然交接），建立 `RateStage::new(INTERNAL_CHANNELS as usize, INTERNAL_SAMPLE_RATE)`，依來源類型設定是否啟用速度/節奏/音高。
76: - `apply_dsp_block(&self, frame: &[f32; 2], out: &mut Vec<f32>)`：餵入一立體聲幀 `[L, R]`，輸出零到多個處理後樣本追加至 `out`：
77:   1. 取得 `FxParams` 快照（`EqShared` 版本號，即時生效，參數不在區塊中途突變）；
78:   2. EQ（每聲道獨立，現有 `eq_processor`）；
79:   3. 速度/節奏/音高（`RateStage.run(input, &fx_params, flush, out)`，依 `FxParams`；電台略過 RateStage）；
80:   4. `FxChain` 音效（bass/enhancer/voice_remover/chorus/flanger/echo/reverb，立體聲幀 `&mut [f32; 2]`）；
81:   5. 正規化（`norm_gain`）；
82:   6. 限幅 `clamp(-1.0, 1.0)`。
83: - `next_playing()` 從 `dsp_out` 佇列取樣本回傳；若 `dsp_out` 空且 `track_out` 空，繼續拉取上游 `next_stream()` → `TrackResampler::process()` → 組成立體聲幀 → `apply_dsp_block()` 直到 `dsp_out` 有樣本或上游結束；上游結束且兩佇列皆耗盡則進入軌結束流程（見 4.3）。
84: - `FxChain::frame(f: &mut [f32])` 已依聲道索引處理（`dsp.rs:332-386`），傳入長度為 2 的切片即可正確處理左右聲道。

86: ### 4.3 軌切換與身分/邊界發布
87: 
88: - `TrackResampler.flush_tail()` / `commit_boundary()` / `set_track()` 在軌切換時已由 `sync_identity()`（line 412-481）序列化：先 flush_tail 舊軌尾端 → commit_boundary 寫入邊界 → set_track 切換到新軌。
89: - 軌切換時 `RateStage` 與舊軌尾端的處理順序（參考 `DspSource::fill()` EOF 路徑 `dsp.rs:659-669`）：`sync_identity()` 先以 `TrackResampler.flush_tail()` 將上游舊軌尾端移至 `pending_output`（`playback_pipeline.rs:432-444`）；舊軌尾端樣本先經 EQ（每聲道獨立，與 `apply_dsp_block()` 第 1 步一致），再以 `flush=false` 逐幀送入舊 `RateStage.run()`，讓 WSOLA / Resampler 正常累積與變速/變調處理；全部餵完後，以空輸入呼叫一次 `RateStage.run(&[], &fx_params, flush=true, ...)`，以 `wsola.drain_raw()` / `rs.drain_raw()` 排空內部殘餘（`dsp.rs:550-568`，與來源結束時 EOF 排空同路徑 `dsp.rs:659-669`）。步驟的 `run` 產出（已過 EQ 與 RateStage）僅經後續音效 → 正規化 → 限幅排出，不再重複進入 RateStage 或 EQ，與正常資料的 `apply_dsp_block()`（EQ → RateStage → 音效 → 正規化 → 限幅）於 RateStage 後方階段對齊，確保無縫；最後才捨棄舊 `RateStage` 並建立新實例。故重建不會截斷舊軌尾端。
90: - `dsp_out` 生命週期（R2-4）：
91:   - 自然交接：舊軌輸出完全排完 `dsp_out` 後，才進入下一軌。
92:   - 手動換軌／seek 安裝新來源前：清空 `track_out` 與 `dsp_out`、重設 RateStage 終結狀態，避免舊位置殘留聲音跳出。
93: - `boundary_in_48k` 由 `TrackResampler.boundary_in_48k()` 發布；`boundary_out_48k` 以舊軌最後一個 DSP 輸出幀的位置提交（DSP 檢查點映射列為待實作，`playback_pipeline.rs:53-55` 目前僅為註解，實際 453-455 行直接使用 `current_boundary_out_start()`，初值為 0）。

95: ### 4.4 錯誤處理
96: 
97: - `TrackResampler` 為 `None` 時（長檔載入失敗）：記錄 `log_line`，`next_playing()` 輸出靜音幀，不 panic。
98: - `RateStage` / `FxChain` 處理錯誤：現有 `log_line` 記錄，輸出靜音幀，不中斷播放。
99: - `next_stream()` 回傳 `None`（串流來源結束）：上游只 flush 一次（`flush_tail`）→ 全部尾端樣本先經 EQ → 舊 `RateStage`（`flush=false` 全部餵入，最後單次 `flush=true` 排空殘餘）→ 音效 → 正規化 → 限幅 → 進 `dsp_out`；`dsp_out` 耗盡後進入 `WaitingForNext`。`RateStage` 只終結一次，不可重複呼叫 `flush_tail()` 或再次 flush 上游（rubato `process_partial(None)` 是補零區塊，非「是否已排空」的查詢，重複呼叫會反覆產生輸出，無法穩定進入等待分支）。

3: # [#3]P0-Imp1Imp3-長檔TrackResampler與DSP鏈
4: 
5: ## Description
6: 長檔（串流軌）繞過 TrackResampler，直接進入輸出，未經重取樣到固定 48kHz。`apply_dsp()` 僅套用 EQ 與正規化，缺少殘響、節奏、音高、回音等 DSP 鏈。長檔播放時無法走 TrackChain→TrackResampler→DSP→DeviceConverter→Sink 的長駐管線。
7: 
8: ## User Story
9: 作為使用者，播放超過 15 分鐘或長度不明的音檔時，樣本應經 TrackResampler 重取樣到 48kHz 後再進入 DSP 與輸出；DSP 鏈應包含除 EQ/正規化外的音效（殘響、節奏、音高、回音等），長檔與短檔走同一條處理路徑。
10: 
11: ## To Reproduce
12: 不適用（非 bug）。
13: 
14: ## Expected behavior
15: - `TrackResampler` 在長檔串流路徑中被配置（`set_track` 指定原生取樣率/聲道）；
16: - `next_playing()` 中串流樣本也經過 `TrackResampler::process()` 重取樣到 48kHz；
17: - `apply_dps()` 套用 `FxChain`（殘響、節奏、音高、回音等），不只 EQ 與正規化。
18: 
19: ## Acceptance Criteria
20: - [ ] 長檔串流樣本經 TrackResampler 重取樣到 48kHz；
21: - [ ] `apply_dsp()` 套用 FxChain（含殘響、節奏、音高、回音等）；
22: - [ ] `cargo test --release --manifest-path src-tauri/Cargo.toml` 全過；
23: - [ ] `npx tauri build` 成功。

41:

85: ## Symphonia 解碼限制（SE7）
86: 
87: - 配置前封包上限預檢 `precheck_packet_budget(path)`：在 `SymStream::open()` 之前執行，讀取檔案標頭遍歷所有音軌與片段的宣告封包大小（MP4 解析 stsz box；其他格式無法可靠遍歷時回傳 Ok，fail-open，依賴 `refill()` 第二層防護）；若任何封包宣告大小超過 256 KB，不呼叫 `open()`，回傳錯誤。
88: - `refill()` 第二層防護順序：取得封包 → 檢查 `packet.buf().len() > 256 KB`（超過即 `finished = true` 回傳 `false`）→ 音軌篩選 → `decoder.decode()`；大小檢查在音軌篩選之前，覆蓋所有音軌與後續片段。
89: - 四個 `SymStream::open` 入口（`player.rs:405`、`playback_pipeline.rs:1586`、`next_track.rs:92,298`）均先呼叫 `precheck_packet_budget(path)`，超標則拒絕不呼叫 `open()`。
90: - 解碼錯誤 `decode_errors` 欄位跨封包累計（`refill()` 迴圈內），超過 10 次即 `finished = true` 回傳 `false`；錯誤與成功封包交錯時仍繼續累計，不歸零。

5: ## 播放與播放模式
6: 
7: ```mermaid
8: sequenceDiagram
9:   participant U as 使用者
10:   participant FE as Shell.tsx
11:   participant AE as AudioEngine
12:   U->>FE: 點兩下一首歌
13:   FE->>AE: player_load(path, songId)（會開始播）
14:   FE->>AE: player_play（保險）、player_set_volume(音量)
15:   FE->>AE: 依模式決定是否 player_preload(下一首)
16:   loop 每 250ms
17:     FE->>AE: player_status
18:     AE-->>FE: position、duration、ended、error…
19:   end
20:   AE-->>FE: ended = true（Sink 播空了）
21:   alt 順序模式
22:     FE-->>U: 停住，不接下一首
23:   else 單曲循環
24:     FE->>AE: 重新播同一首
25:   else 全部循環／隨機
26:     FE->>AE: player_load(下一首)
27:   end
28: ```
29: 
30: - 四種模式：**順序**（這首播完就停）、**全部循環**、**隨機**、**單曲循環**。模式按鈕旁要顯示文字，而且順序與全部循環的圖示和顏色要不同。
31: - 手動按下一首永遠會換歌；單曲循環只在自然播完時重播同一首。
32: - 引擎不能自己接預載的下一首（這會繞過模式）。之後做無縫播放時，改成「引擎只接前端依模式預載的那一首」。
33: - `player_load` 會開始播；要停在某個位置但不出聲，用 `player_prepare`。先載入再暫停會漏出一點聲音。
34: - `player_load` 之後要直接呼叫 `playerSetVolume(音量)`，不能用 `muted ? 0 : 音量`，否則剛開始播的聲音會被歸零。
35: - 15 分鐘以上（或長度不明）的檔案用串流播放：不做峰值正規化，也不參與交叉淡化。交叉淡化只在兩首都是記憶體軌、而且模式是全部循環或隨機時混音。
36: - symphonia 0.5 不會修剪 AAC 開頭的 2112 個 priming 樣本（約 44ms），這是固定的，不是 seek 的 bug。
37: 
38: ## 工作階段（重新開啟時接回進度）
39: 
40: - 存在 `app_config.session`。只在暫停、切歌、關閉時寫入，位置最多每 5 秒寫一次；不在 250ms 輪詢時寫。
41: - 啟動時停在上次的歌曲與位置，**不自動播放**。不存電台，也不自動重連電台。
42: - 曲庫裡已經不存在的 id（歌曲或佇列）直接丟掉，不報錯。
43: - 右鍵開啟與工作階段恢復同時發生時，以右鍵開啟的檔案為準：恢復流程的 token 要在任何 `await` 之前取樣（`openWithRestore.ts` 的 `sessionRestoreActions`）。

45: ## 右鍵開啟與拖放
46: 
47: ```mermaid
48: sequenceDiagram
49:   participant W as Windows
50:   participant N as 新程序
51:   participant R as 執行中的實例
52:   participant FE as Shell.tsx
53:   W->>N: sonicledger.exe "C:\a.flac"
54:   N->>N: audio_arg() 從 argv 找出音訊路徑
55:   alt 已經有實例在跑

75: ## 曲庫與搜尋
76: 
77: - 缺檔標成 `missing=1`，不刪除列；掃描一個資料夾時，不能標記資料夾以外的歌。
78: - 音軌號與碟號存正整數或 NULL，不存 0。專輯檢視依碟號、音軌號、歌名排序；最近播放依播放時間排序。這兩個都不套用曲庫的排序鍵。
79: - 搜尋：每個詞都要符合（AND）。3 個字以上用 FTS5 trigram `MATCH`（任意位置的子字串、不分大小寫）；1–2 個字改用 `LIKE`。比對範圍是曲名、歌手、專輯、去空白的拼音、拼音首字母。搜尋結果要套用到清單上，不能只存在本機狀態裡。
80: - 歌曲清單必須虛擬捲動，10 萬首也不能一次畫成 DOM。
81: - 封面路徑是檔案系統路徑，要用 Tauri 的 file-src 轉換才能顯示。

83: ## 掃描與標籤限制（SE7）
84: 
85: - lofty 讀取標籤前設定單欄 ≤ 4 KB、總標籤 ≤ 16 KB 上限；超過 16 KB 的總標籤拒絕整檔入庫（`Rejected`），單欄超 4 KB 由 `limited_tag()` 第二層裁切並記 `ScanError`，不中斷其他欄位。
86: - 不載入嵌入封面進記憶體：掃描前先執行 `has_embedded_cover_precheck(path)` 偵測 ID3v2 APIC、MP4 `covr`、FLAC 圖片區塊；偵測到嵌入封面直接拒絕入庫，不走 lofty 也不走 ffprobe 後備；`cover_path` 固定為 `None`。
87: - 取樣率驗證 8000–384000 Hz、聲道 1–8，超出視為無效（含 0 值）；不使用 `.filter(|v| *v > 0)` 過濾零值，先檢查 0 值再檢查範圍，非法值拒絕入庫並記 `ScanError`。
88: - ffprobe 後備讀取的標籤進入共同處理前，套用相同 4 KB／16 KB 預算。
89: - 掃描結果契約：`ScanResult::Song(NewSong, Vec<ScanError>)` 正常入庫、`ScanResult::Rejected(Vec<ScanError>)` 拒絕入庫但錯誤仍彙整、`ScanResult::Skipped` 檔案系統層級跳過；單一檔案錯誤不導致整個掃描失敗。

91: ## 歌單
92: 
93: - 頁籤就是工作區：開歌單會釘一個頁籤，關頁籤不會刪歌單；「全部歌曲」永遠在。開著的頁籤存在 `playlist_tabs`。
94: - 側欄不放刪除按鈕；「全部歌曲」「最近播放」是檢視，不能刪。
95: - 排序寫入用 `playlist_items.id`，不是 `song_id`。
96: - 智慧歌單依規則重算，不存項目，不能拖曳或移除項目。規則只能用欄位白名單（`query_smart_playlist_songs`），不接受自由 SQL。
97: - m3u：只處理 UTF-8 的 `.m3u` 與 `.m3u8`。相對路徑以 m3u 所在的資料夾展開。對不到的行逐一列出，不能默默丟掉。

99: ## 等化器與音效
100: 
101: - 18 段半八度：31、63、87、125、175、250、350、500、700、1K、1.4K、2K、2.8K、4K、5.6K、8K、11K、16K。各段與前級都是 ±15 dB，有總開關（關閉時各段與前級都不作用）。
102: - `design_gains` 解各段之間的互相干擾，讓每段中心頻率的實際響應等於推桿值；畫面上的曲線由 `eq_response_cmd` 用同一套算出來，不能在前端另算一套近似值。
103: - 十種音效：速度、節奏、音高、低音、高音增強、人聲消除、合唱、鑲邊、回音、殘響。全部關閉時輸出要跟輸入逐樣本相同。速度、節奏、音高不作用於電台。
104: - 改參數時不重開音源（不能每拖一下推桿就 `restart_from`）。
105: - 預設 `{ name, bands, preamp?, bind? }`。種子是本播放器自己調的曲線，只在沒有同名預設時補上；使用者可以覆寫、刪除。
106: - 自動套用的比對順序：綁定這首檔案 → 綁定這張專輯 → 綁定這個曲風 → 依曲風的內建建議 → 回退預設。每首歌只在換到它時套用一次，之後使用者手動調整不會被蓋回去。
107: - 情境建議會一次替換等化器、前級與音效；音效從預設值開始覆寫，不保留上一個情境的設定。
108: 
109: ## 工具
110: 
111: - **批次標籤**：只改歌手、專輯、曲風、年份，不在同一批裡改曲名或音軌號。失敗的檔案逐一列出，不能用「整批成功」帶過。
112: - **轉檔**：本機有 ffmpeg 才執行，沒有就明說。mp3 顯示 128／192／320 kbps 選項，flac、wav、ogg 不顯示位元率。不顯示假的進度條。
113: - **電台**：只收使用者貼的 http/https 網址，不內建電台目錄，也不猜 ICY 資訊；ICY 的 stream title 持續顯示。電台用 ffmpeg 轉成 PCM 播放，沒有 ffmpeg 就明說。

4: 
5: ## Description
6: 長檔（串流軌）繞過 TrackResampler，直接進入輸出，未經重取樣到固定 48kHz。`apply_dsp()` 僅套用 EQ 與正規化，缺少殘響、節奏、音高、回音等 DSP 鏈。長檔播放時無法走 TrackChain→TrackResampler→DSP→DeviceConverter→Sink 的長駐管線。
7: 
8: ## User Story
9: 作為使用者，播放超過 15 分鐘或長度不明的音檔時，樣本應經 TrackResampler 重取樣到 48kHz 後再進入 DSP 與輸出；DSP 鏈應包含除 EQ/正規化外的音效（殘響、節奏、音高、回音等），長檔與短檔走同一條處理路徑。
10: 
11: ## To Reproduce
12: 不適用（非 bug）。
13: 
14: ## Expected behavior
15: - `TrackResampler` 在長檔串流路徑中被配置（`set_track` 指定原生取樣率/聲道）；
16: - `next_playing()` 中串流樣本也經過 `TrackResampler::process()` 重取樣到 48kHz；
17: - `apply_dps()` 套用 `FxChain`（殘響、節奏、音高、回音等），不只 EQ 與正規化。
